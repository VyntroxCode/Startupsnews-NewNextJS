AWS Lambda Migration Plan

How startupnews.fyi moves from its single EC2 server to AWS Lambda — what runs today, what changes, what it costs, and the exact order of work. Companion to Product.html and arch.md.

Plan only — nothing built yet 2026-09-28 AWS 654654388388 · us-east-1 Next.js 16.1.6 Live site unaffected

Section 1

Why move, and what was decided

The whole site — pages, admin panel, database, cache, and five scheduled jobs — runs on one EC2 machine (m5a.xlarge). If that machine fails, everything is down, and someone has to maintain it: OS updates, disk space, PM2 processes, nginx. On Lambda, AWS runs the servers and the team only ships code.

Cost is roughly neutral (Section 5), so the reason to migrate is operational: no server to patch, automatic scaling, a managed database with automated backups.

DecisionChoiceWhy
Deployment toolSST v3 + OpenNextThe standard Next.js→Lambda adapter; the whole stack is defined in one file in the repo and deployed with one command. OpenNext supports Next 16.
DatabaseRDS MariaDB db.t4g.small, single-AZ, + RDS Proxyzox_db is only 211 MB. The Proxy is required: the current server peaked at 121 DB connections, and Lambda multiplies connections.
RedisElastiCache Serverless (Valkey)Drop-in Redis replacement; the only app change is REDIS_URL=rediss://… (TLS). Current Redis holds ~4 MB.
Scheduled jobsEventBridge Scheduler → LambdaReplaces the PM2 cron process and the crontab entry.
RolloutStaging copy first; production DNS stays on EC2 until manually flippedZero risk to the live site while validating.
WordPressNot migrated — databases already deleted (2026-09-28)WordPress had been dead since Jan 2026; ~26 GB reclaimed.

Code changes required

Nine focused changes, all safe to run on EC2 too. They were prototyped in a working session on 2026-09-28 and then fully reverted at the owner's request — the repo is untouched. This list is the exact to-do for when the build is green-lit.

#File(s)Change & why
1src/app/actions/upload-image.ts + 6 more new S3Client(…) sites (s3-presign.ts, image-to-s3.ts, 4 presign routes)Breaks on Lambda today. They pass AWS_ACCESS_KEY_ID/SECRET explicitly; on Lambda those hold temporary role credentials that are invalid without the session token. Add one shared helper: use static keys when no session token is present (EC2), otherwise let the SDK's default chain sign (Lambda).
2src/lib/rate-limit/incubatx-rate-limiter.ts + 6 caller routesSilently stops working on Lambda. The in-memory Map is per-process; each Lambda container would count separately. Port to Redis INCR + PEXPIRE (falls back to the Map when Redis is down); callers add await.
3src/shared/database/connection.tsGuard process.env.TZ='Asia/Kolkata' behind !AWS_LAMBDA_FUNCTION_NAME (TZ is reserved on Lambda; the pool already pins +05:30). Run with DB_CONNECTION_LIMIT=2 (web) / 4 (cron) instead of the default 18.
4src/shared/locks/redis-lock.tsacquire() quietly returns true when Redis is unreachable, i.e. overlap protection vanishes silently. Keep fail-open but log at error level so it is visible. EventBridge retries set to 0 on the RSS rule as the second guard.
5next.config.tsAdd outputFileTracingIncludes for data/partner-logos.snapshot.json (read at request time via process.cwd(); would fail on Lambda). Append the CloudFront/production domains to serverActions.allowedOrigins.
6api/admin/contacts/import, api/admin/partnership-events/importmaxDuration 900 → 60. The UI sends 300-row batches that finish in seconds; CloudFront cuts requests at 60 s regardless.
7api/admin/rss-feeds/[id]/fetchAdd maxDuration = 60 — the "Fetch now" button runs a full feed fetch in-request with no limit today.
8sst.config.ts (new)The entire infrastructure as code: VPC, RDS + Proxy, Valkey, NAT, the Next.js app, 3 cron schedules, secrets. ~200 lines. RDS/Proxy/Valkey use raw Pulumi resources inside SST (SST's built-ins are MySQL/cluster-shaped).
9functions/cron/*.ts (3 new files)Thin Lambda handlers that reuse the existing job classes. The RSS handler replaces the in-memory queue: fetch due feeds, process 4 at a time in-process (144 feeds max, all currently disabled — no queue service needed).
Deliberately left alone The proxy's per-article self-fetch (works, costs a second invocation — optimize later), the local-disk upload fallback (dead code, S3 is configured), the admin queue-status page (already shows zeros today), and cron/index.ts/PM2 (untouched until cutover so EC2 keeps working as-is).

Section 6

Build order
  1. Branch + tooling. git checkout -b feat/sst-lambda-migration; npm i -D sst@3; gitignore .sst/, .open-next/.
  2. App fixes. Changes 1–7 from Section 4. Verify with tsc --noEmit and a local build; all changes are EC2-safe.
  3. Infrastructure. Write sst.config.ts (Section 4, #8) and the three cron handlers (#9).
  4. Secrets. npx sst secret set for DbPassword, JwtSecret (same value as production so admin logins carry over), SmtpPass, TurnstileSecret, AmazonPaSecret, CronSecret. Non-secrets into .env.staging. Drop the dead WP_* vars; never set AWS_* (reserved on Lambda).
  5. Deploy staging. npx sst deploy --stage staging — first run takes ~20 min (RDS is the slow part). Confirm the partner-logos snapshot landed in the server bundle.
  6. Load the database. Runbook in Section 7.
  7. Validate. Checklist in Section 8; let staging soak a few days with 1–2 RSS feeds enabled.
  8. Cutover. Runbook in Section 9 — only on explicit go-ahead.

Section 7

Database migration runbook
  1. Temporarily make the RDS instance publicly accessible with a security-group rule allowing only this EC2's IP /32 (the old and new VPCs are separate; peering is overkill for 211 MB). ~10-minute window.
  2. Dump from the EC2 box: 
    mysqldump --single-transaction --quick --routines --triggers zox_db \
  > ~/dumps/zox_db_$(date +%F).sql
  3. Restore into the RDS instance endpoint (not the proxy): 
    mysql -h <rds-endpoint> -u zox -p zox_db < ~/dumps/zox_db_<date>.sql
  4. Spot-check row counts (posts, rss_feeds, site_settings) against the source.
  5. Flip the instance back to private and remove the temporary rule immediately.
  6. Schema migrations after that: keep the existing scripts/deploy.sh flow (scripts/migrations/*.sql + manifest), run from this EC2 box against RDS through the same temporary window. This box stays the single migration runner until it is retired.

Section 8

Staging validation checklist
  • Home, category, author, and article pages render; an edited post appears within 60 s (ISR)
  • Legacy WordPress URLs return 410 with the right robots header
  • Admin login; post create/edit with image upload (proves the S3 credential fix + allowedOrigins)
  • Contacts and partnership-events XLSX imports (300-row batches)
  • Report page-count route (pdf-lib), search, sitemaps, llms.txt, /_next/image
  • Rate limiter returns 429 under hammering (proves the Redis port)
  • RSS: enable 1–2 feeds in the staging DB → post created within 10 min, images in S3
  • Publishers cron: schedule a post 5 min out → auto-publishes
  • Newsletter handler exits cleanly with the DB gate off
  • RDS Proxy pinning metric stays low; cold-start p99 acceptable; ROBOTS_NOINDEX=1 present on staging

Section 9

Cutover and rollback
  1. Deploy the production stage; issue an ACM certificate (us-east-1) for startupnews.fyi, DNS-validated via Cloudflare.
  2. Announce a ~15-minute admin write freeze, early morning IST. pm2 stop zox-cron; comment out the crontab RSS line.
  3. Final dump/restore (Section 7 — a full replace of the RDS copy).
  4. Flip the Cloudflare origin from the ALB to the production CloudFront domain. Under Cloudflare proxying this takes effect immediately.
  5. Watch CloudWatch (5xx, Lambda errors, proxy connections) and Cloudflare analytics for 24–48 h.
Rollback is one step Flip the Cloudflare origin back to the ALB and restart zox-cron + the crontab. The EC2 box stays fully working until explicitly decommissioned. Caveat: admin writes made after the flip live only in RDS — either reverse-dump them back or accept the loss, decided at flip time.
