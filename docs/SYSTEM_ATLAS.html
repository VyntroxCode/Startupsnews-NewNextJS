Overview

StartupNews.fyi is a single Next.js 16 App Router codebase with no ORM — every module talks to MariaDB through hand-written SQL behind a repository layer. Six functional areas share that codebase: the public news/events site, an admin panel, a lighter publisher/event-admin dashboard, an employee/HR portal, a sales & partnerships tracker, and an RSS ingestion pipeline that feeds both the site and the newsletter.

System Architecture

Every read or write follows the same shape: route/page → service (business rules + cache) → repository (raw SQL) → MariaDB, with Redis as a read-through cache and lock provider, and S3 as the media store. A separate cron/queue/worker track runs outside the request cycle for RSS ingestion and scheduled publishing.

No shared session table — every flow is stateless JWT. Staff tokens are checked against a fixed role→permission map in src/shared/middleware/roles.ts (e.g. HR_TOOL_ROLES and SALES_TRACKER_ROLES are admin-only). Employee tokens reload the credential row on every request so deactivation takes effect immediately.

Read path — cached post list request

sequenceDiagram
    participant B as Browser
    participant R as /api/posts route
    participant C as Redis cache
    participant SV as PostsService
    participant RP as PostsRepository
    participant DB as MariaDB

    B->>R: GET /api/posts?filters
    R->>RP: publishScheduledPosts()
    RP->>DB: UPDATE posts SET status='published' WHERE due
    R->>C: getCache(api:posts:filters)
    alt route cache hit
        C-->>R: cached JSON
        R-->>B: 200 response
    else route cache miss
        R->>SV: getAllPosts(filters)
        SV->>C: getCache(posts:all:filters)
        alt service cache hit
            C-->>SV: PostEntity[]
        else service cache miss
            SV->>RP: findAll(filters)
            RP->>DB: SELECT ... FULLTEXT / LIKE
            DB-->>RP: rows
            RP-->>SV: PostEntity[]
            SV->>C: setCache 60s
        end
        SV-->>R: PostEntity[]
        R->>R: entitiesToPosts()
        R->>C: setCache api:posts:filters, 60s
        R-->>B: 200 response
    end
Posts are cached at two layers — the route's serialized-filter key and the service's query key — both 60s TTL for list views, 600s for single-post-by-slug. Any write invalidates every posts:* / post:* / api:posts:* prefix via a SCAN+DEL sweep. Redis is fail-soft: if it's unreachable, cache calls become no-ops and the app just reads straight from MariaDB.

The in-memory queue (src/queue/queue.memory.ts) is single-instance and unpersisted — jobs live in a Map with exponential-backoff retry, not backed by Redis despite Redis being used elsewhere. An admin "Fetch now" button bypasses the queue and calls the worker directly.

Background Jobs & Queues

A standalone daemon (cron/index.ts, run via npx tsx cron/index.ts) owns five node-cron schedules, each guarded by a Redis lock plus an execution-timeout guard to prevent overlap across instances. The same jobs are also reachable over HTTP for external schedulers.

Database Schema

MariaDB, no ORM — 53 tables across 6 domains. scripts/init-db.sql only covers the original 8 tables; everything since (audit columns, SEO fields, HR tool, banners, reports, RSS, sales, partnerships) was added via one-off migration scripts. Some tables self-provision their own DDL from application code rather than a tracked migration. Full detail on both in Notes & Caveats below.

Notes & Caveats

Six things worth knowing before treating this as ground truth for a migration or a new feature.

  • scripts/init-db.sql is not a clean day-one baseline. It's been silently updated over time to fold in some early migrations (audit columns, panel_admins, admin_tools visibility flags) but not later ones — SEO fields, event venue/country fields, and all of HR tool, banners, reports, RSS, sales, and partnerships. Treat it as authoritative only for users, categories, posts, post_tags, events, analytics, sessions, settings, admin_tools.
  • The real migration history lives in git, not on disk. Every file under scripts/migrations/*.sql was deleted from the working tree after being run; only a 4-line .applied_migrations log and git history remain. Recoverable via git log --all --diff-filter=A --name-only -- 'scripts/migrations/*.sql'.
  • Five tables self-provision their own DDL from application code rather than a tracked migration: reports/report_sections, brand_stories/brand_story_sections, event_regions, public_registrations (+2 child tables), and site_settings.
  • Flagged discrepancy — events.status. Application code writes 'draft'/'completed' values not present in any tracked ENUM migration; the live database enum was likely altered outside the tracked migration flow. Verify against production schema before relying on the enum list shown here.
  • Two dead tables: sessions and analytics exist in the baseline schema but no current repository code queries either — auth is fully stateless JWT, and view counts/trending scores are written straight onto the posts row instead.
  • Duplicate self-migration on posts.is_gone_410. It has both a tracked migration and a second, independent defensive ALTER TABLE inside src/app/api/admin/posts/bulk-status/route.ts — same end state, two code paths creating it.
